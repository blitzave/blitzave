In April I launched BlitZave. It was a finance app with a Next.js front end, a FastAPI back end, Postgres, and hosting on Vercel. It had sign-up, sessions, encrypted bank credentials, and a categorizer with an LLM at the bottom of it.

Today BlitZave is a Python program you run on your own laptop. No accounts. No server. No hosting bill. Your money data is one file in your home folder.

Getting from there to here took three architecture switches between June and October. Some of them were good calls. At least one was a way to avoid a hard problem. This is the honest version.

## Version one: built like a startup

The first BlitZave was built the way you're supposed to build a product. FastAPI and Postgres (after a detour through MongoDB), Next.js on Vercel, JWT auth, bank credentials encrypted at rest, and SimpleFIN for read-only bank access.

And it worked. I launched it, wrote the posts, and used it every day.

The problem was that I couldn't maintain it. A lot of it had been generated faster than I understood it, so every change meant re-learning a piece of my own app. When your own code is a stranger to you, every fix is a guess.

## Switch one: into the browser

In June I started over as an offline-first web app: Vite, React, and all the data in the browser's own storage. No server at all.

The reasons sounded great together. It would feel instant on my phone. Hosting would cost nothing. Nobody's money would sit on a server.

It lasted twenty days.

## Switch two: back to the cloud

What ended it was a list. I wrote down the three things I wasn't willing to give up:

1. **Alerts that reach you when the app is closed.** An insight that shows up thirty days after the purchase is a filing cabinet.
2. **Bank sync every few hours**, without anyone opening anything.
3. **Categorization you set up once** and never think about again.

All three need a machine that's always on. An app that only runs when you open it can't do any of them. I also wanted to share it with friends and family who aren't technical. They need an account on a website, not a database in their browser that they have to back up themselves.

So I deleted the browser version and went back to the cloud app.

Looking back, that reasoning holds up. So does the lesson I wrote down that day:

> Name the real driver before you choose the tech.

The real driver in June was "it should feel instant on my phone." A cloud app can get that with caching. I didn't need to throw out the server for it.

## What three months in the cloud looked like

This is the part I didn't see coming. Going back to the cloud was the right call for the product I'd described. It was the wrong call for the product I actually had, which had one user: me.

A lot of that summer went into things only a hosted app needs: accounts, auth, sessions, scheduled jobs, credential encryption, deploys. And the codebase kept surprising me:

- A feature I'd marked as shipped in April lived on a branch I had never merged. The dashboard was calling endpoints that returned 404, and its friendly "no data yet" empty state hid the failure. I found out in July.
- I'd built a tidy-looking stack, `api → services → repositories`, plus a "contracts" layer to bridge them. The bridge caused a circular import that worked one way and failed under the test runner.

None of that was hard on its own. But all of it was work for users who didn't exist yet. Meanwhile the thing I actually wanted, an app that tells me whether my money habits are working, wasn't getting any closer.

## Switch three: coming home to 127.0.0.1

On October 18th I started a new repo with one rule: **build for one.** One process, one data file, one command to start.

- A Python server that listens only on `127.0.0.1`. It's never exposed to the network it's sitting on.
- SQLite. Your money data is one file in `~/BlitZave`.
- The SimpleFIN credential lives in the OS keychain, never in the database.
- The same process serves the UI, so the local API never has to accept requests from other sites. (That one gets its own post.)
- It syncs with your bank when it starts, so the one thing worth knowing is already on the page when you open it.

Thirteen days later there was a release you install with one command. By November 8th it had budgets, savings goals, and a Home page that shows one sentence.

That pace isn't because I got faster. It's because most of what I'd been building wasn't there anymore.

## What I gave up

I want to be straight about this, because the July list didn't stop being true. Running locally gives up all three:

- **No alerts.** If BlitZave isn't running, it can't reach you.
- **No sync while the laptop is closed.** It catches up when you start it.
- **No easy sharing** with family who don't use a terminal.

Those are real losses, and they're still good ideas. They're just later problems. Building them first had cost me shipping anything at all.

## Why this one stays

Honestly, a fourth switch is the thing I'm guarding against most. Switching architectures feels like progress. You get a fresh start with none of the old mess. That's exactly why it's dangerous. More than once, a hard task looked to me like an architecture problem.

So this time the decision comes with a written condition for reopening it:

> If I stop opening the app because nothing reaches me, alerts are needed, and that means an always-on machine. Then the engine moves to that machine. It doesn't get rewritten.

That's the real difference. Not that local beats cloud. It's that the next move is already decided, and it doesn't start from zero.

## What survived every switch

The architecture changed four times. The product barely changed at all.

Be an ally, never a scorekeeper. Report what you're doing, never scold it. Show the one thing that matters and keep the depth one tap down. Bank access stays read-only. All of that was written down in June, during the switch I reversed, and it carried through every move since.

The tech was wrong more than once. The idea never was.

## If I were starting again

- **Build for the users you have.** If that's one person, build for one.
- **Name the real driver.** "It should feel instant on my phone" is a caching problem, not a rewrite.
- **Before you switch, write down what would make you switch back.**
- **Check the code, not your notes,** to know what's shipped.

**Try it.** BlitZave is open source and runs on a Mac (Linux should work too). The [guide](../../guide/) takes you from install to your first month in about ten minutes. If you've made your own cloud-to-local switch, or the other way around, I'd like to hear how it went on [Discord](https://discord.gg/akSZ794XxG).
